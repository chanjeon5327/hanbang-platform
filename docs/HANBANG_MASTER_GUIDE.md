# HANBANG(한방프로젝트) — Project Profile for Cursor AI

## 0. 프로젝트 한 줄 정의
HANBANG은 "유튜브 채널/웹툰/웹소설 등 디지털 IP의 수익권(또는 지분)을 조각화하여 투자·거래"할 수 있는 모바일 중심 플랫폼이다.
핵심은 (1) 주문/결제 (2) 원장(ledger) 기반 자산관리 (3) 정산(판매자 지급) 불변성/감사로그 (4) 업비트형 거래 + 토스형 금융 + 넷플릭스형 큐레이션 UX 결합이다.

## 1. 기술스택/런타임
- Front: Next.js 16.1.x (dev는 turbopack 불안정 → `next dev --webpack` 사용)
- Lang/Style: TypeScript, TailwindCSS, Pretendard 폰트
- Backend: Supabase (Auth + Postgres + RLS + RPC)
- Wallet/Web3: wagmi + MetaMask (모듈/확장 관련 이슈 대응 경험 있음)
- Package: pnpm
- OS/환경: Windows 개발(포트 3000 충돌/.next/dev/lock 등 중복 프로세스 이슈 있었음)

## 2. 설계 원칙 (중요)
### 2.1 원장(ledger) 불변성
- "잔고/보유자산/정산"은 모두 ledger_entries 같은 원장 이벤트로 증명 가능해야 함.
- 주문 상태 전이(예: paid→completed→settled) 시점에 원장 기록이 자동 생성/고정되어야 함.
- PG 심사용: "정산은 재수정 불가, 감사로그 남음, 스냅샷 해시/락 등으로 중복 방지"가 핵심.

### 2.2 보안
- Supabase RLS/RBAC 적극 사용
- Service Role Key는 서버 전용(클라이언트 노출 금지)
- 관리자 기능은 audit log + 권한 체크 + (필요 시) 트랜잭션 락으로 무결성 유지

### 2.3 UX 디자인 합의
- 정적 페이지(메인/지갑 등): 토스 스타일 금융 UI
- 콘텐츠 큐레이션/레일: 넷플릭스/OTT 스타일
- 거래(호가/차트/주문): 업비트/코인원 스타일
- 썸네일 퀄리티와 폰트가 전체 퀄리티를 좌우
- 히어로(브랜딩): "H 폭발"급 강한 인트로(1~3초 영상/이미지)로 첫인상 압도

## 3. 현재까지 확인된 기능/현황(요약)
### 3.1 인증(Auth)
- 이메일 로그인/회원가입 동작 확인 경험 있음
- LoginModal이 "준비중 alert"를 띄우던 문제 → /login으로 이동하도록 변경한 이력
- 카카오/구글 OAuth 로그인도 동작 확인 이력
- 로그아웃 UI가 2개(헤더 중복)로 세션/로컬스토리지 불일치 가능성 이슈가 있었음

### 3.2 지갑/원장(ledger) & 주문(orders)
- /wallet에서 사용자 원장(ledger_entries) 조회하여 잔고/내역 표시하는 구조
- "주문 completed 시 구매자 원장(CASH_DEBIT/ASSET_CREDIT) 자동기록" 같은 자동기록 플로우 구축 이력
- 관리자 정산 확정 시 orders.status → settled, ledger_posted_at 채움, 재수정 불가 기준을 목표로 진행

### 3.3 관리자 정산(핵심)
- rpc_admin_confirm_settlement 같은 RPC로 "정산 확정(상태 settled 전이)" 성공 경험 있음
- admin_audit_logs 등 감사로그 스키마/NOT NULL 컬럼 이슈를 겪으며 보완해온 이력
- 정산은 '불변'이 핵심(중복 실행 방지, 스냅샷/해시/락 등)

### 3.4 거래 UI
- MobileProductHeader, MobilePriceChart, OrderBookPanel/Summary, MobileOrderPanel, StickyBar 등
- 목표: "업비트형 호가창+차트+매수/매도 UX" 완성

### 3.5 온보딩(채널평가 온보딩)
- 왓챠처럼 "나이/성별 묻지 않고", 유명 유튜브 채널 카드 다수 노출 → 사용자가 간단 액션(평가/좋아요/별점)만 하면
  채널의 태그/속성(장르, 크리에이터 타입 등) 중첩으로 취향 벡터를 만든다.
- taste_score / personalized_score 같은 뷰를 만들려 했으나,
  테이블(예: user_interest_ratings) 미존재/뷰 의존성 순서 문제 등 SQL 이슈가 있었음.
- 목표: 개인화 추천 레일 + 전환 퍼널(관심등록→상세체류→매수 버튼)로 연결.

## 4. 당장 앞으로 구현할 기능 (우선순위)
1) 거래 UX 마감: 호가/차트/주문 패널, 주문 생성→결제→완료까지의 "실제 구매 플로우"
2) 출품자(크리에이터) 기능: 상품(수익권) 등록/관리, 정산 내역 확인, 정산 요청/상태 확인
3) 관리자 기능 강화: 주문/정산 모니터링, 확정 버튼, 감사로그/원장 검증, 불변성 강화
4) PG 결제 붙이기(예: KCP): 결제요청/콜백검증/주문상태 전이/원장기록 자동화
5) 보안/RLS/RBAC/비밀관리: 정책 정리 + 로그/감사 + 운영체계 확립
6) 성능/정리: /wallet 중복 렌더, 헤더 중복, 이미지 404 경고, dev 성능 저하 등 청소

## 5. 개발 규칙(주인님 규칙) — 반드시 준수
### 5.1 '커명'(Cursor 명령) 규칙
- 가능한 한 "한 번에 실행 가능한 터미널 명령 묶음"으로 제시한다.
- Windows/PowerShell 기준 명령을 우선으로 한다.
- 목표: 주인님이 기계적으로 복붙 실행만 해도 진행되게.

### 5.2 '통코'(통째 코드) 규칙
- 수정이 필요한 파일은 "파일 경로 + 파일 전체 코드(통코)"를 우선 제공한다.
- 부분 패치는 통코가 불가할 때만.
- 코드 블록에는 반드시 경로를 명시한다.

### 5.3 답변 형식(두괄식 피드백)
항상 아래 순서로:
1) 지금 당장 해야 할 액션
2) 어디/무엇을 어떻게(통코 우선)
3) 최종 체크 기준
(이유/배경 설명은 마지막)

### 5.4 작업 방식
- 한 번에 다중 대안 나열보다: 해결책 1개 → 결과 공유 → 다음 스텝(반복)
- 원인분석 필요하면 캡처/로그/코드 복사를 적극 요청해도 됨

## 6. Git 커밋 규칙
- 커밋 메시지는 가급적 한글
- 커밋 메시지 마지막에 "YYYY-MM-DD HH:mm" 타임스탬프 포함

## 7. 용어
- Gate-1/2/3: 런칭 기준 마일스톤(지갑/정산/PG 등)
- 정산 불변성: 정산 확정 후 재수정 불가 + 감사로그 + 원장/스냅샷으로 증명 가능
- 채널평가 온보딩: 카드 평가로 취향벡터 생성(개인화 추천에 사용)

# 2) 사업모델 정리 (KCP/온보딩 포함)

## 2.1 사업의 본질

크리에이터/IP의 미래 현금흐름(광고·협찬·구독·2차 저작 등)을 상품화하고,

사용자는 조각 단위로 구매/보유/거래하며,

플랫폼은 결제·원장·정산·거래 UX를 표준화해 "IP를 금융상품처럼" 다루게 만드는 모델입니다.

## 2.2 참여자(3자 구조)

구매자/투자자: 원화로 결제 → 수익권(또는 지분/토큰화된 권리) 매수 → 보유/거래 → 배당·정산 수취

출품자/크리에이터(판매자): 상품 등록(채널/작품 단위) → 판매/유통 → 정산 받음

관리자(운영/컴플라이언스): 상품 심사/정산 확정/분쟁 대응/감사로그/리스크 관리

## 2.3 돈 버는 지점(수익원)

거래 수수료: 매수/매도 체결 시 일정 %

출품 수수료/등록비: 상품 등록(검수/심사/콘텐츠 패키징 비용)

정산 수수료: 판매자 정산 실행(정산 주기·금액·건수 기반)

프리미엄 구독: 고급 데이터(분석/리포트), 빠른 체결/알림/툴, 크리에이터 운영 도구

B2B 제휴: MCN/에이전시/콘텐츠 제작사에 "유통·정산 인프라" 제공

## 2.4 KCP(PG) 붙이는 이유와 위치

사용자 관점: "원화로 바로 사는" 경험이 있어야 대중화됩니다(카드/계좌이체 등).

운영/심사 관점: PG(예: KCP)는 정산·환불·분쟁·부정거래를 매우 민감하게 봅니다.
그래서 HANBANG은 원장 기반 불변성 + 감사로그 + 상태전이 증빙으로 "PG 심사에 강한 구조"를 만들려는 방향입니다.

구현 관점(흐름):

주문 생성(order)

KCP 결제 요청(redirect/결제창)

결제 콜백/검증(서버)

orders.status = paid/completed 전이

ledger_entries 자동 기록

정산 배치 생성 → 관리자 확정 → settled 전이

## 2.5 온보딩(채널평가 온보딩)의 "사업적 역할"

단순 재미가 아니라, 개인화 추천 → 전환율 상승이 목적입니다.

왓챠 방식처럼:

"나이/성별/직업" 같은 민감 질문 대신

인기 유튜브 채널 카드 다량 노출 → 사용자가 별점/좋아요로 평가

채널 태그(장르/톤/주제/시청자층/형식 등) 중첩 → 취향 벡터(그래프) 생성

이후 메인 레일/상세 추천 이유/알림까지 연결

결과: 신규 유저가 들어오자마자 **'내 취향 투자상품'**이 보이니, "관심등록→상세체류→매수" 퍼널이 빨라집니다.

## 2.6 최종적으로 주인님이 원하는 "그림"

첫 화면은 넷플릭스처럼 쫙 펼쳐진 콘텐츠(채널/작품)

클릭하면 업비트처럼 차트/호가/주문이 즉시 등장

결제는 KCP로 원화 10초 구매

모든 돈의 이동은 ledger로 증명되고

정산은 관리자 확정 후 불변(감사로그/스냅샷/락)

이 구조 자체가 "플랫폼의 신뢰"가 되어 투자자/PG/파트너를 설득하는 무기가 됩니다.
