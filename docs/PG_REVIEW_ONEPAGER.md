# Cursor "1페이지 System Prompt" (초압축/즉시이해용)

# YOU ARE CURSOR AI — HANBANG Project Context (1-page)

## Project
HANBANG(한방)은 유튜브 채널/웹툰/웹소설 등 "디지털 IP 수익권(또는 지분)"을 조각화해
사용자가 원화로 매수/보유/거래하고, 크리에이터는 판매/정산 받는 모바일 중심 플랫폼.

## Tech Stack
- Next.js 16.1.x + TS + Tailwind(Pretendard)
- Supabase(Auth + Postgres + RLS + RPC)
- pnpm / Windows
- dev는 `next dev --webpack` 안정 (turbopack 불안정 이력)
- 거래 UI: 업비트형(차트/호가/주문) + 정적 UI: 토스형 + 큐레이션: 넷플릭스형

## Core Principles (Non-negotiable)
1) Ledger-first / Immutability:
- 잔고/보유/정산은 "원장(ledger_entries)" 이벤트로 증명 가능해야 함.
- 주문 상태 전이(paid→completed→settled) 시점에 원장 자동기록/고정.
- 정산 확정 후 재수정 불가(감사로그/스냅샷/락 등) = PG 심사 대응 핵심.

2) Security:
- RLS/RBAC 기본. Service Role Key는 서버 전용(클라 노출 금지).
- 관리자 행위는 audit log 남기고 권한 체크 + 중복 실행 방지.

## What's already done / known issues (high level)
- 이메일 로그인/회원가입, OAuth 동작 확인 이력
- 로그인 모달 → /login 이동 수정 이력

## Dev Rules (must follow)
- "커명": 가능한 한 터미널에서 그대로 실행 가능한 명령 묶음으로 제시(Windows/PowerShell 우선).
- "통코": 수정 시 파일 경로 + 파일 전체 코드(통코) 우선. 부분패치는 불가할 때만.

# PG 심사용 "1장 요약" (정산 불변성/증빙 구조)

# HANBANG — PG 심사용 1장 요약 (결제·원장·정산 불변성)

## 1) 서비스 개요
- 디지털 IP(유튜브 채널/웹툰 등)의 수익권/지분을 조각화하여 사용자가 원화로 구매/보유/거래.
- 핵심 신뢰장치: "주문·결제·정산" 전 과정을 원장(ledger)과 감사로그로 추적 가능하게 설계.

## 2) 결제(예: KCP) 처리 구조 — 서버 검증 중심
- 주문 생성(order): 금액/상품/구매자/상태(pending) 기록
- PG 결제 요청: 결제창/리다이렉트 방식 (클라이언트는 결제 시작만)
- 결제 완료 콜백/웹훅: 서버에서
  - (a) PG 응답 서명/파라미터 검증
  - (b) 주문 금액/주문번호 매칭 검증
  - (c) 중복 콜백 방지(아이템포턴시 키/락)
- 검증 성공 시 상태 전이:
  - pending → paid → completed(서비스 정책에 맞게)
- 환불/취소 시에도 서버에서 동일하게 검증 및 상태 전이/원장 반대분개로 추적.

## 3) 원장(ledger) 기반 회계/자산 추적 (Immutable Ledger)
- 모든 금전/자산 변화는 ledger_entries 이벤트로만 발생:
  - 예: CASH_DEBIT, CASH_CREDIT, ASSET_CREDIT, ASSET_DEBIT 등
- 잔고/보유자산은 "누적 합계"로 계산되며, 특정 시점의 상태는 원장으로 재현 가능.
- 원장 레코드는 생성 후 수정 금지(정책상 UPDATE 차단, 필요 시 반대분개로만 조정).

## 4) 정산(판매자 지급) 불변성 설계 (핵심)
- 정산은 배치(settlement_batch) 단위로 생성:
  - 대상 기간/판매자/대상 주문 집합/금액 합계 확정
- 정산 확정(관리자):
  - 트랜잭션 내에서
    1) 중복 실행 방지 락(예: advisory lock 등)
    2) 대상 주문 상태를 settled로 전이
    3) ledger_posted_at(또는 동등 필드) 기록
    4) 스냅샷(대상 주문/합계) 생성 + 해시(무결성 증빙) 저장
    5) 감사로그(admin_audit_logs) 기록
- 확정 후 재수정 불가:
  - settled 상태 주문은 변경 제한(RLS/정책/트리거)
  - 수정이 필요하면 "정정 배치" + 반대분개 방식으로만 처리(감사 가능).

## 5) 권한/보안(RLS/RBAC/키 관리)
- Supabase RLS로 사용자/판매자 데이터 접근 분리.
- 관리자 API는 서버에서만 Service Role 사용(클라이언트 노출 금지).
- 관리자 행위는 모두 감사로그로 남기며, 대상/행위/시간/주체 추적 가능.

## 6) 운영 증빙(감사/분쟁/정산검증) — 제출 가능 산출물
- 주문 단건: 주문ID 기준으로
  - 주문 생성 시점, PG 검증 로그(서명검증/금액매칭), 상태 전이 이력,
  - 원장 기록(구매자 차감/자산부여), 환불 시 반대분개
- 정산 배치: 배치ID 기준으로
  - 대상 주문 목록 스냅샷 + 해시,
  - 확정 시각, 확정 관리자, 전이된 주문 수, 정산 금액 합계,
  - 원장 반영 여부(ledger_posted_at), 재수정 차단 근거

## 7) 리스크 통제 포인트(요약)
- 결제 위변조: 서버에서 서명/금액/주문번호 검증
- 중복 결제/중복 콜백: 아이템포턴시/락/상태 체크로 차단
- 부정 정산: 배치 스냅샷+해시, 감사로그, 확정 후 변경 불가
- 데이터 노출: RLS/RBAC, Service Role 서버 전용, 로그 기반 추적
